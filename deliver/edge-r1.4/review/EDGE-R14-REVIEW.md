## A. Zero trading effect: yes

- Readers of every new piece of state (grep over live-executor.js, lib/*.js, tmc-proxy.js, health-watchdog.js):
  - `latestControlAlt`: only `appendJournal` -> `controlParity.annotate` (journal rows) and its own stats (live-executor.js:2553-2568, :2998). One call site; test/control-parity.test.js also asserts no other lib mentions it.
  - Scorecard `tp1t`, `rs`, `agg.t1/ny/rs`: only scorecard.js itself, surfaced through `score.view()` into the snapshot (live-executor.js:5009). No gate reads `score.view()`.
  - `dayRisk` / `day.risk`: only the snapshot writer (live-executor.js:5141). `dayRiskView` calls `enrichTradesWithJournal` on a slice and `phoneSnap.exitReasonOf`; both return copies (spread) or read-only lookups.
- Shared state in the second evaluation: `evaluateLevelsPro` builds a fresh `cfg` from defaults + the spread options on each call; no module-level cache or Map in levelsPro.js, alignmentFreshness.js or helpers.js; the one place it sorts copies the bars first (`[...bars].sort`). `levelsParityOpts()` is a pure function of CONFIG (no shared flag); the alt options come from a frozen constant spread into a new object. My test (h/purity.js, 2000 15m bars + all higher frames, 'cme' anchor, 5m VWAP, measured alignment, both formulas as used): inputs unchanged after both runs (JSON snapshot equal), the used result array byte-identical before and after the alt run, both directions ('pine' used / 'off' used). Control score used by the gate is `lvByTf.M15.biasScore` = the same `levelsOut` last row the alt step compares against (live-executor.js:2688), so the comparison is like for like.
- Throw safety: the whole `controlAltStep` body is in try/catch (live-executor.js:2556-2568), runs after the real `levelsOut` is assigned and before it is used, resets `latestControlAlt` to null on error. The stats call at the end of the evaluation is separately wrapped. The async ordering is unchanged: the step is synchronous inside the existing synchronous evaluation block.
- Timing: the evaluation is one synchronous block, so the alt run delays the rest of that poll by the alt time (measured on my boot: 949 ms on the cold warm-up evaluation, avg 499 ms per run, +20% over the 10-minute window with 14 of 26 evaluations near the line; max block 3.8 s at warm-up). Intrabar evaluation runs every 20 s, the order poll is in the same loop, stops rest at the broker. I found no timer, watchdog or staleness check keyed to evaluation duration: alignment freshness is 'measured' (live config), which does not use the 60 s read-age rule; `alignNowMs` for the 15m call is taken before the alt run. The 5m/3m evaluations that follow stamp `Date.now()` up to 0.5 s later; that only matters at an HTF period boundary, the same exposure any slower evaluation has. Not testable on the virtual-clock rig.

## C. Proxy streaming

- Byte-identity: 70 requests (28 of the builder's kind on a 93 MB journal incl. limits 0, -5, abc, 1, 99999, unknown/odd filters, three real trade ids, unknown id, malformed id, other symbol, missing day, both downloads; plus 43 on a hostile journal: filter words inside other fields, loose closed/pending rows, spaced JSON, CRLF, a 2.8 MB multi-byte line across 1 MB chunks, empty and blank lines, garbage line, torn unterminated last line). Status line, every header (Date stripped) and body sha256 equal old vs new in all 70 (the first run's single difference was my harness missing the socket 'drain' relay; fixed, then equal, including the 93 MB and 5 MB downloads). Headers identical, including Content-Type, Content-Disposition and the absence of Content-Length.
- Growing file: appending one whole row every 2 ms (appendFileSync, like the bot) during a download and during four route requests on a 40 MB journal: the download is exactly the first `size at open` bytes (sha equal to that prefix), ends on a newline; other routes answered 200. Reads are bounded by the size at open, so rows appended mid-request are not seen; the `/signal-journal` second pass is bounded by the first pass's `limit`. A row only half written at the instant of the stat could appear torn at the end, exactly as the old whole-file read could; the unterminated last line is included as before.
- Rotation / truncation: the bot never renames or truncates the journal (grep). A file that shrinks between the two passes of `/signal-journal` reads fewer bytes; no crash (`min(end, size)`), answer may differ from the old one. Not an event that occurs.

## G. Re-freeze 79b3c3b (emit-once, null journalId, hand-over)

Suite test/emit-once.test.js: 11 pass (Node 18). My own scenarios: h/restart.js, h/final.js.

1. EMIT-ONCE.
 (a) Rollback: a state file written by 79b3c3b (extra top-level key `emitted`, plus `agg.t1/ny/rs`, `tp1t`, `rs`) loads on r1.3 (not corrupt, view works, saves). r1.3 ignores `emitted`; in my run the key survived the r1.3 save. Even if a rollback dropped it, only records still unsettled could re-emit, and r1.3 folds those without emitting, so no row is written twice.
 (b) 600-key cap: at most 3 keys per trade, so 600 keys = the last 200 trades. A key is only consulted while its record is still in st.recs (kept at most 50 on load; a record waits at most 6 h for money). A key cannot fall out before its record is settled. Safe.
 (c) settle(): a record is folded and spliced in the same step, and emitOnce saves the whole state, so the file never holds a record both folded and listed. Kill points: after key persisted, before append: row lost, record still listed, next settle sees 'dup', folds once. After append, before fold saved: same, folded once. After fold saved: gone, counted once. Not found: any path that counts twice or zero times. Scenario with restart mid-trade: totals counted 1 trade, three rows (runner_shadow, tp1_touch, ny_late_trade) one each. Caveat (existing, not new): a restart that changes the record id leaves two records for one trade and one of them waits 6 h for money, then is counted as moneyMissing (seen with null journalIds, h/restart.js 'nulljid2').
 (d) Unwritable state file (parent path is a file): no throw, no row written, the record stays listed and is retried at every poll, main loop continues. Cost: a failed synchronous save plus a log line twice per poll (10 lines in 5 polls) until the disk recovers. A `runner_shadow` row whose emitOnce fails is not retried (its state is already resolved), so that one record-only row is lost; `tp1_touch` and `ny_late_trade` are retried.
2. NULL-JOURNALID TRADES. Confirmed on a trade whose restored view has no journalId and no earlier record: no `tp1_touch`, `runner_shadow` or `ny_late_trade` row is written; tp1t is counted unresolved with why 'no journalId'; the runner shadow is an unresolved record with the same why. (Both rows null: records stay listed until the 6 h money wait ends, as before.) When the journalId is the same, the record id is just the journalId, so the restart continues the same record (flag `cont` false, shadow keeps running). Hand-over only applies when the old record was closed in the very same poll, same direction, entry within 0.26, journalId not different: with a different journalId (J2 after J1) no hand-over, each trade keeps its own watchers (tested); with a null journalId it adopts the old one's (tested). A different trade could only receive a shadow if one position ended and another same-direction entry within a tick started in the same poll with an unknown journalId: not a realistic case. The NY-late and TP1-touch fold of the continuation is skipped (`cont`), so it is not counted twice.
Finding 1 still stands: install all six files (79b3c3b changes lib/scorecard.js only, hash 8e5d1cc2).
